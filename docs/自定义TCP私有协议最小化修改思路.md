# 私有协议 V1 最小化修改方案（已评审修订）

## 1. 结论

V1 采用“少改现有 Modbus 主链路、先把私有 TCP 协议跑通”的方案，整体可行，但必须把“服务类型”和原有 `protocol_type` 分开：

- `connections.service_type` 表示连接承载的业务服务类型：`0=Modbus`，`1=私有协议`。
- 现有 `connections.protocol_type` 仍只表示 Modbus 内部的 TCP / RTU over TCP / Auto，只有 `service_type=0` 时才有意义。
- 旧数据和旧客户端请求默认视为 `service_type=0`，升级后原 Modbus 配置不受影响。
- `service_type` 创建后不可切换；如需切换协议，应新建连接。
- 私有协议配置单独放入 `private_protocols` 表，并通过独立接口维护。
- V1 只支持 HEX 存储、完整匹配、分隔符分帧、响应随机占位符。
- 私有协议连接不允许新增/修改 Modbus `slaves/registers`；迁移时不自动删除历史残留数据，避免升级误删。

## 2. 数据结构

### 2.1 `connections`

新增字段：

```sql
ALTER TABLE connections ADD COLUMN service_type INTEGER NOT NULL DEFAULT 0;
```

含义：

| 值 | 含义 |
|---|---|
| `0` | Modbus |
| `1` | 私有 TCP 协议 |

### 2.2 `private_protocols`

```sql
CREATE TABLE IF NOT EXISTS private_protocols (
    id TEXT PRIMARY KEY,
    conn_id TEXT NOT NULL UNIQUE,
    name TEXT NOT NULL,
    frame_delimiter_hex TEXT NOT NULL,
    rules_json TEXT NOT NULL,
    FOREIGN KEY(conn_id) REFERENCES connections(id) ON DELETE CASCADE
);
```

一条连接最多一套私有协议配置。

## 3. 规则 JSON

```json
{
  "name": "规则1",
  "matchMode": 0,
  "requestHex": "AA01",
  "responseHex": "BB@RCC",
  "randomConfig": [
    { "token": "@R", "min": 1, "max": 255, "widthBytes": 1 }
  ]
}
```

约束：

- `matchMode` V1 仅允许 `0`，表示完整匹配。
- `requestHex` 不包含分隔符。
- `responseHex` 不包含分隔符，可包含随机 token。
- `randomConfig.token` 必须形如 `@R` / `@TEMP1`，且必须出现在 `responseHex`。
- `widthBytes` 允许 `1-8`，随机值转为固定宽度大写 HEX，不足左补 `0`。

## 4. API

### 4.1 创建连接

```http
POST /api/connections
```

```json
{
  "name": "自定义TCP设备",
  "port": 2502,
  "serviceType": 1
}
```

旧请求不传 `serviceType` 时后端按 `0=Modbus` 处理。

### 4.2 查询私有协议配置

```http
GET /api/connections/{connId}/private-protocol
```

如果连接是私有协议但尚未保存配置，返回默认草稿：

```json
{
  "connId": "...",
  "name": "连接名",
  "frameDelimiterHex": "0D",
  "rules": []
}
```

### 4.3 保存私有协议配置

```http
PUT /api/connections/{connId}/private-protocol
```

保存时后端会校验 HEX、分隔符、匹配模式和随机 token。

### 4.4 删除配置

```http
DELETE /api/connections/{connId}/private-protocol
```

删除连接时，`private_protocols` 通过外键级联删除。

## 5. TCP 运行时

当 `service_type=1`：

1. TCP listener 启动后不进入 Modbus 解析器。
2. 按 `frame_delimiter_hex` 从 TCP 字节流切帧。
3. 对帧内容转大写 HEX，和规则里的 `requestHex` 做完整匹配。
4. 命中后渲染 `responseHex`，替换随机 token。
5. 响应内容追加分隔符后写回 TCP 连接。
6. 未命中规则时不响应。

## 6. 前端

V1 前端采用独立“私有协议”管理入口，避免重构现有设备树。该入口支持：

- 新建/编辑私有协议连接
- 配置分隔符 HEX
- 以 JSON 编辑规则
- 插入示例规则
- 删除私有协议连接

后续版本可再把私有协议节点完全并入设备树和 Tab 编辑器。

## 7. 前端页面重构建议（推荐作为 V2）

### 7.1 顶部一级切换

不建议继续把“私有协议”做成一个临时弹窗入口，推荐改成页面顶部一级切换，且**标题和一级 Tab 放在同一行**：

```text
+----------------------------------------------------------------------------------+
| 设备模拟器                                              [ Modbus ] [ 私有协议 ]   |
+----------------------------------------------------------------------------------+
```

设计原则：

- `Modbus` 和 `私有协议` 是两个一级工作区，不共用同一套编辑版面。
- 顶部栏保持单行：左侧产品标题，右侧一级切换 Tab。
- 点击顶部 Tab 后切换主内容区，不弹窗。
- 各自记住最近一次选中的连接和编辑状态。
- 切换前如果有未保存修改，提示用户“保存 / 放弃 / 取消”。
- 可用 URL hash 或 query 保留状态，例如：
  - `#/modbus`
  - `#/private-protocol`

### 7.7 为什么推荐这种版面

相对当前“弹窗 + 单段 JSON”的方式，这套版面的优点更明显：

- 把 `Modbus` 和 `私有协议` 的心智模型彻底分开
- 树形交互几乎直接复用 Modbus，学习成本最低
- 私有协议只保留一层树，结构更直观
- 右侧主界面直接就是“发什么 / 回什么”的对照表
- 右侧没有多余层级，打开就是表格，认知成本最低
- 连接属性移出主工作区后，操作焦点更集中
- 更适合后续增加规则数量、优先级、测试能力
- 页面明显比“三栏 + 基础配置 + 多模式切换”更简单
- 后续如果支持前缀匹配、校验位、脚本响应，也更容易扩展

### 7.8 实现建议

V2 前端重构时，建议：

- 后端接口先保持不变，优先只重做前端页面结构
- 页面状态拆分为：
  - `modbusViewState`
  - `privateProtocolViewState`
- 私有协议页面先复用现有接口：
  - `GET /api/connections/tree`
  - `POST /api/connections`
  - `PUT /api/connections/{id}`
  - `DELETE /api/connections/{id}`
  - `GET /api/connections/{id}/private-protocol`
  - `PUT /api/connections/{id}/private-protocol`
- 当前 V1 弹窗入口可保留一版作为过渡，但最终应下线，避免双入口造成混乱。
